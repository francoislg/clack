## Why

When `add-trivia-game-cascade-tier` shipped the `trivia_management` integration in May, it explicitly deferred two pieces of follow-up work and labeled them as "future primitives": (1) flipping the trivia-management instruction from baseline (`addInstruction`) to topic-scoped (`addTopicInstruction`) once the parallel `add-plugin-topic-instructions` change landed, and (2) building actual tool-topic gating in the SDK so the management tools only become callable after `attach_integration("trivia_management")`. The parallel change landed; both follow-ups never did. The result is a fiction: the catalog advertises `trivia_management` as a real integration, but the instructions load as baseline anyway, the tools are always callable, and `attach_integration("trivia_management")` is a no-op that sets a session flag nobody reads.

This is causing observable harm. Claude sees `upsert_season` as freely available but reads the catalog framing for `upsert_game` as gated behind an attach step, so it picks the season-tier tool when admins say "update the game" — the path of least resistance wins. The fix is to make the gating real and to widen the integration to cover every config-mutation tool, so "management" becomes a coherent toolkit instead of an arbitrary three-tool slice.

## What Changes

- **NEW (SDK primitive)** — `sdk.registerTool(minRole, tool, mapping)` gains an optional fourth parameter for topic gating. When set, the tool is hidden from the assembled tool catalog unless the topic appears in `session.attachedIntegrations`. Without the parameter, behavior is unchanged.
- **NEW (SDK primitive)** — `sdk.registerTopic(name, { description, alwaysLoad? })` — plugins can declare their own catalog-only virtual integrations without touching `data/config.json`. Plugin-contributed entries merge into the effective MCP registry at boot, so `attach_integration(name)` validates and the integration appears in the system-prompt catalog. Collisions with a `data/config.json` entry of the same name throw at plugin-load time.
- **NEW (capability)** — `trivia-management-tools`: a coherent toolkit for admin-initiated config mutation, gated behind `attach_integration("trivia_management")`. Owns the topic instruction, the (now plugin-declared) catalog entry, and the seven config-mutation tools.
- **MODIFIED (membership)** — Four tools move into `trivia_management`: `upsert_season`, `delete_season`, `add_categories`, `remove_categories`. Combined with the three already-named tools (`upsert_game`, `delete_game`, `set_workspace_config`), the integration covers all seven admin-initiated config-mutation operations.
- **MODIFIED (instruction wiring)** — `TRIVIA_MANAGEMENT_INSTRUCTION` flips from `addInstruction` to `addTopicInstruction` keyed to `"trivia_management"`. The instruction is rewritten to enumerate all seven tools (currently lists three) and to include the dispatch heuristic ("game" → `upsert_game`, "season" → `upsert_season`, etc.).
- **REMOVED (config leak)** — `data/config.json` `mcpServers.trivia_management` is deleted. The trivia plugin self-declares the integration via `sdk.registerTopic("trivia_management", { description, alwaysLoad: false })` at plugin load time. Plugin-owned concepts no longer leak into bot-level config.
- **MODIFIED (runtime-only tools stay always-available)** — Tools called during cron-fired flows (`get_ideas`, `save_question`, `post_questions`, `get_question_history`, `submit_answers`, `process_reveal_answers`, `check_season_status`, `save_cheating`) and read-only inspection tools (`list_games`, `list_seasons`, `find_previous_questions`, `retrieve_scores`) keep their current always-registered status — they are NOT moved into the integration.
- **CLEANUP** — The stale "Once `add-plugin-topic-instructions` lands…" comment at `src/plugins/trivia/prompts/triviaCheckInstruction.ts:200-203` is deleted; the comment at `src/plugins/trivia/index.ts:111-114` is rewritten to describe the topic-gated reality.

## Capabilities

### New Capabilities
- `trivia-management-tools`: The `trivia_management` integration. Covers (a) the catalog entry and its description contract, (b) the topic-scoped admin instruction that documents the seven tools and the dispatch heuristic, (c) the seven config-mutation tools (`upsert_game`, `delete_game`, `set_workspace_config`, `upsert_season`, `delete_season`, `add_categories`, `remove_categories`) gated to admin role AND attached topic, (d) the no-op semantics when an admin session has not attached the topic (tools are hidden from the catalog entirely).

### Modified Capabilities
- `clack-plugins`: The `ClackSdk Interface` requirement and `registerTool` requirements extend to accept an optional `topic?: string` parameter. The tool-server assembly path adds a topic-membership filter alongside the existing minRole filter. NEW requirement adds `sdk.registerTopic` so plugins self-declare catalog-only integrations; `PluginLoadResult` carries the contributions; the MCP registry resolver merges plugin-contributed entries into the effective registry.

## Impact

- **Code**: `src/plugins/sdk.ts` (SDK signatures + JSDoc — `registerTool` options + `registerTopic`), `RegisteredTool` interface (new `topic` field), `PluginLoadResult` (new `integrations` field), `src/plugins/lifecycle.ts` or wherever `harvest()` is called (collect integration declarations), `src/mcp.ts` `resolveEffectiveRegistry()` (merge plugin contributions + collision check), `src/tools/server.ts:448-468` (topic-filter in plugin tool assembly), `src/plugins/trivia/index.ts` (seven `registerTool` calls add `{ topic: "trivia_management" }`; instruction registration flips to `addTopicInstruction`; new `sdk.registerTopic("trivia_management", ...)` call), `src/plugins/trivia/prompts/triviaCheckInstruction.ts` (rewrite `TRIVIA_MANAGEMENT_INSTRUCTION` to enumerate seven tools; delete stale comment).
- **Config**: `data/config.json:167-170` entry **deleted**. The integration now lives entirely in the trivia plugin.
- **Tests**: SDK unit test for topic-gated `registerTool`; integration test asserting an admin session without attach sees zero of the seven management tools; integration test asserting the same session AFTER attach sees all seven. Existing trivia tool tests should continue to pass (the tool functions themselves don't change).
- **Behavior change** (positive): Claude in an admin session no longer sees seven config-mutation tools in its baseline catalog. It must call `attach_integration("trivia_management")` before touching any of them. The catalog description is now load-bearing, not theater.
- **Behavior change** (potentially breaking for in-flight sessions): A session that was using the management tools without an explicit `attach_integration` call will, post-deploy, find those tools missing. Cron-fired sessions are unaffected (they never used these tools). Admin reactive sessions will get a one-turn detour where Claude calls `attach_integration` then proceeds — the catalog framing already prompts this behavior, so the detour should be invisible to the user beyond a slight latency on the first management request per session.
- **No data migration needed.** The change touches code paths and prompt text; persisted state (`config.json`, `seasons.json`, `categories.json`) is untouched.
