## Why

The trivia plugin's data is workspace-global today: every question, answer, cheat report, and season is mixed into the same flat files at `data/plugins/trivia/`. That makes it impossible to test new trivia features (a different question-type mix, a fresh season, an experimental prompt rewrite) without polluting the main game's question history, leaderboard, and duplicate-detection corpus. Adding a "games" namespace — one per Slack channel hosting trivia — gives admins a structurally isolated sandbox: a `sandbox` game can run alongside `initialgame` with completely separate questions, answers, cheats, and season timelines.

A parallel piece of work (already on disk) introduced `config.trivia.games[]` to make trivia channels **declarative**: each entry produces two plugin-managed cron jobs (question + reveal) via `buildGameSpecs()` + `sdk.reconcileCronJobs("trivia", ...)`. That change replaces the old admin-runs-`create_schedules_instructions` setup recipe, but doesn't add data isolation. This change layers data isolation on top of the declarative-config foundation.

## What Changes

**Builds on (already-on-disk):**

- `config.trivia.games[]: { name, channel, questionCron, revealCron, timezone, enabled? }` — declarative trivia channel registry.
- `buildGameSpecs(games, seasonsEnabled)` → `CronJobSpec[]` — produces plugin-managed cron specs.
- Migration `019-trivia-games-migration` — converts legacy `trivia` cron jobs into `config.trivia.games[]` entries.
- Deletion of `createSchedulesInstructions`, `sendQuestionsInstructions`, `processResponsesInstructions` MCP tools (scheduled prompts are now constants inlined by `buildGameSpecs`).

**Adds (this change):**

- **Per-game directory layout.** All per-game data lives under `data/plugins/trivia/games/<name>/{questions,answers,cheats,seasons}.json`. `categories.json` and `users.json` stay at the trivia root, shared globally.
- **Required `game: string` argument on every per-game trivia tool**: `get_ideas`, `save_question`, `find_previous_questions`, `get_question_history`, `submit_answers`, `retrieve_scores`, `save_cheating`, and (when seasons enabled) `check_season_status`, `upsert_season`, `delete_season`, `list_seasons`. The slug is validated against `config.trivia.games[].name`; unknown name → structured error; entry with `enabled: false` → structured "game is disabled" error on writes (reads still succeed, frozen-archive semantics).
- **`list_games` MCP tool** (member role) — reads `config.trivia.games[]` and returns the list (optionally including `enabled: false` entries). No `create_game`/`disable_game`/`enable_game` tools — games are lifecycle-managed by admins editing `config.trivia.games[]` (which the plugin reconciles into cron specs on every load).
- **`config.trivia.games[].enabled?: boolean` flag** (defaults to `true`). When `false`: `buildGameSpecs` skips the entry (no cron jobs reconciled) AND write tools refuse for that name. Reads still succeed.
- **`config.trivia.games[].name` validation strengthens**: `^[a-z0-9-]+$`, length 1–32. The existing parser already rejects empty names and duplicates; this change adds format + length validation alongside. Invalid entries are dropped with a logged warning (consistent with the existing dropping behavior).
- **Migration 019 extended** — the pre-existing `019-trivia-games-migration` (cron-jobs → `config.trivia.games[]`) is extended to also move legacy flat-file data into a per-game directory. The destination is selected in this order: (1) the first newly-created `legacy-<channel>` entry from this run, (2) the first pre-existing `config.trivia.games[]` entry, (3) a fallback `initialgame` entry (placeholder crons + `enabled: false`). Fresh deployments with no schedules AND no flat data write nothing. The migration is idempotent.
- **Per-game seasons.** `seasons.json` moves into each game's directory. All season tools take `game` and operate on `games/<name>/seasons.json`. The plugin-load-time seasons bootstrap (today: writes `seasons.json` once) is rewritten to run **per-game at the time the game first runs**: when any tool resolves `game = "X"` and finds no `games/X/seasons.json` while `trivia.seasons.enabled` is true, the plugin seeds the starter season into `games/X/seasons.json` lazily. (This avoids tying the season bootstrap to a `create_game` event that doesn't exist in the config-driven model — admins just add a config entry.)
- **Channel→game inference for reactive sessions.** A helper (`resolveGameFromChannel(channelId)`) consults `config.trivia.games[].channel` and returns the matching `name` (or `null`). DMs / mentions in a configured channel resolve transparently; uncontactable contexts (DM channel not in any game) refuse with a clear error. The `triviaCheckInstruction` advertises this so Claude knows to invoke the helper before any trivia tool call.
- **Scheduled-prompt updates.** `SEND_QUESTIONS_INSTRUCTIONS` and `getProcessResponsesInstructions()` constants in `scheduledPrompts.ts` gain a `{game}` placeholder. `buildGameSpecs.ts` substitutes the game name into each spec's `prompt` so Claude receives `"Game: <name>. ..."` at the top of every scheduled run and knows to pass `game: "<name>"` on every tool call.
- **`triviaCheckInstruction` mentions `list_games`** and the per-game scoping model.

## Capabilities

### New Capabilities

- `trivia-games`: the `config.trivia.games[]` schema + format validation, per-game directory layout (`data/plugins/trivia/games/<name>/...`), the universal `game`-arg invariant on per-game tools, the `enabled: false` semantics (skip cron reconcile + refuse writes), the `list_games` tool, the channel→game inference helper for reactive sessions, the extended migration 019 (cron jobs + flat data → declarative games model), and the rule that game lifecycle (create/rename/delete/disable) is admin-edited-config, not tool-managed.

### Modified Capabilities

- `trivia-question-search`: `save_question`, `find_previous_questions`, and `get_question_history` gain required `game: string`. The slug is validated against `config.trivia.games[]`. Each tool operates exclusively on `games/<name>/questions.json`. Duplicate detection is strictly per-game.
- `trivia-batch-answers`: `submit_answers` and `retrieve_scores` gain required `game: string`. Per-user stat aggregation is scoped to the named game's `answers.json` only. The global `users.json` continues to receive auto-registration writes (users span games).
- `trivia-cheating-detection`: `save_cheating` gains required `game: string`. Cheat reports go to `games/<name>/cheats.json`; the global `users.json#cheatAttempts` counter is incremented cumulatively across all games.
- `trivia-seasons`: `seasons.json` moves to `games/<name>/seasons.json` (per-game timelines). All season tools (`check_season_status`, `upsert_season`, `delete_season`, `list_seasons`) gain required `game: string`. Slug uniqueness and no-overlap invariants are enforced per-game. The plugin-load-time seasons bootstrap is replaced with **lazy per-game seeding**: when a tool first resolves a game whose `games/<name>/seasons.json` is absent (with `trivia.seasons.enabled` true), the plugin creates it with a starter season.
- `trivia-scheduled-prompts`: the `send_questions_instructions`, `process_responses_instructions`, and `create_schedules_instructions` MCP tools are **REMOVED** — superseded by `buildGameSpecs` baking the prompt constants directly into `CronJobSpec.prompt` at reconcile time. The prompt constants (`SEND_QUESTIONS_INSTRUCTIONS`, `getProcessResponsesInstructions()`) gain a `{game}` placeholder that `buildGameSpecs` substitutes with each spec's game name. Every tool-call step inside those prompts is rewritten to pass `game: "<name>"`.
- `trivia-categories`: unchanged in storage (categories remain global). No requirement changes.

## Impact

- **Code**: `src/plugins/trivia/` — `data.ts` (add `loadGames` / `resolveGameFromChannel` / `forGame(name)` scoped accessor), `index.ts` (register `list_games`, remove the global plugin-load seasons bootstrap, keep the `buildGameSpecs` + `reconcileCronJobs` wiring), every tool file to add the `game` arg and route through `data.forGame(name)`, `scheduledPrompts.ts` (add `{game}` placeholder substitution), `buildGameSpecs.ts` (substitute `{game}` and respect `enabled: false`), `triviaCheckInstruction.ts` (mention games / channel inference / `list_games`). New files: `gameName.ts` (format validation helper), `gamesRegistry.ts` (`requireGame` / `requireWritableGame` / `resolveGameFromChannel`), `listGames.ts`.
- **Config**: `config.ts#TriviaGame` gains optional `enabled?: boolean`. `parseTriviaGames` adds `^[a-z0-9-]+$` length 1–32 validation on `name`, and accepts the optional `enabled` field (defaults to `true`).
- **Migration**: existing blocking migration `019-trivia-games-migration` is extended to also move legacy flat data into a per-game directory. The target game name is chosen via the inheritance order above; only deployments with legacy flat data AND nothing to inherit from get the fallback `initialgame` entry. Idempotent.
- **Data files**: per-game directories under `data/plugins/trivia/games/<name>/`. `categories.json` and `users.json` unchanged.
- **Tests**: `parseTriviaGames` format-validation cases (uppercase, whitespace, too long, path-traversal chars), `enabled` flag parsing. `forGame(name)` accessor tests. Per-tool `game`-arg tests (cross-game isolation, unknown-name rejection, disabled-name write refusal + read pass-through). Channel-inference helper tests. Migration 019 extension tests (fresh deployment writes nothing; flat data + dispatcher → data lands in `legacy-<channel>`; flat data + pre-existing config game → data lands in first existing entry; flat data + nothing → fallback `initialgame`; idempotency on the data move). Per-game season tests (same slug across games is OK, per-game no-overlap).
- **Dependencies**: none.
- **Backward compatibility**: deployments without `config.trivia.games[]` still work for plugin loading. Existing trivia tool calls without a `game` argument fail at the MCP layer (Zod required-field validation) — this is intentional after the migration: every call must specify a game. Migration 019's data-move step ensures legacy data lands somewhere queryable: in the just-created `legacy-<channel>` for single-channel deployments, in the first existing entry for pre-configured deployments, or in a fallback `initialgame` only when there's data but nothing to inherit from. Multi-channel legacy deployments end up with multiple `legacy-<channel>` entries and the historical data in the first one — operators can hand-redistribute if needed.
