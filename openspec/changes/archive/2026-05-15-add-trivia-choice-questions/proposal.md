## Why

The trivia plugin today asks every question in the same shape: a single true-or-false statement voted on with `:+1:` / `:-1:`. That shape has a 50/50 floor (random guessers score 50%), thin variety for long-running channels, and limited game-show energy — multiple-choice is the canonical trivia format and the existing Game Show Presenter persona is shaped for it. Adding multiple-choice questions alongside the existing boolean ones gives a second, harder question shape (1-in-N vs 1-in-2) that also reads more like a real trivia show.

## What Changes

- Add two new optional config blocks: `trivia.questionsTypes` (weighted-random map, e.g. `{ "boolean": 2, "choice": 1 }`) and `trivia.choices = { min: number, max: number }` (defaults `{ min: 2, max: 4 }`). When `questionsTypes` is absent or only contains `boolean`, behavior is unchanged. `trivia.choices` is workspace-scoped only — it is not overridden per-season (it is a card-readability UX setting, not a gameplay parameter).
- Introduce a question-type discriminator on `TriviaQuestion`: `type: "boolean" | "choice"`. Absence of `type` reads as `"boolean"` for legacy rows (no migration).
- For `type: "choice"` questions, store `choices: string[]` (length within `[trivia.choices.min, trivia.choices.max]`, capped at 4) and `correctIndex: number` (0-based, exactly one correct answer).
- Extend `SubmittedAnswer` with an optional `answerIndex: number` field, populated for choice questions (the existing `answer: boolean` continues to be populated for boolean questions).
- Extend `get_ideas` to weighted-randomly roll `suggestedType` from the active type weights, and — when `suggestedType` is `"choice"` — additionally roll `suggestedChoiceCount` uniform in `[min, max]` and `suggestedCorrectIndex` uniform in `[0, count)`. The boolean-path `suggestedAnswer` continues to be rolled when `suggestedType` is `"boolean"`.
- Extend `save_question` to accept `type`, `choices`, and `correctIndex` arguments for choice questions, with validation: exactly one correct index, choices length within configured bounds, no duplicate choice strings.
- Extend `submit_answers` to accept `answerIndex` per answer entry. Correctness for choice answers is `answerIndex === question.correctIndex`. Boolean answers keep the existing `answer === question.isTrue` path. The tool's return shape is unchanged (per-user `correct`, `totalCorrect`, `totalAnswered`, `currentStreak`).
- Rewrite the scheduled question-posting flow (`SEND_QUESTIONS_INSTRUCTIONS`) to branch on `suggestedType`: the boolean path is unchanged; the choice path adds a "write the correct answer first, then distractors" step (mirrors the existing polarity-first gate), a **distractor plausibility gate** (rate each option 1-10; fail-and-rewrite-distractors-only rules; never rewrite the correct answer because that defeats the server-rolled `correctIndex`), a Block Kit choice-card layout (stacked when any choice is long, inline otherwise), and `reactions` array sized to the choice count (`["one", "two", "three", "four"]`, sliced).
- Rewrite the reveal flow (`PROCESS_RESPONSES_INSTRUCTIONS`) to **resolve the question before parsing reactions** (today the order is reversed): the reveal must read `question.type` to know whether to parse `:+1:`/`:-1:` (boolean) or `:one:`/`:two:`/`:three:`/`:four:` (choice). For choice questions: correct = users who reacted with exactly the right-index numbered emoji; incorrect = users who reacted with exactly one wrong numbered emoji; multi-react voters (2+ numbered emoji) are **silently voided** (not scored, not called out); wildcards (non-numbered reactions like `:shrug:`) continue to be read aloud with the persona's interpretive humor.
- Add a hard-failure path to the reveal flow: if the question cannot be resolved (e.g., `find_previous_questions` returns no match) AND the message reactions suggest a choice question, post an admin-facing error rather than guessing — choice reveal cannot proceed without `correctIndex`.
- Compose with the seasons feature (`trivia-seasons` capability, currently being refactored to a timeline model by the in-flight `refactor-seasons-as-timeline` change): when seasons are enabled, `questionsTypes` lives on the per-season `SeasonEntry` record in `seasons.json#seasons[]` (mirroring how `categories` are scoped per-entry today) and overrides the workspace-level `config.trivia.questionsTypes` default for whichever entry is current per `findCurrentSeason(state, now)`. The `upsert_season` MCP tool gains an optional `questionTypes` argument; admins can set it at season creation time or update it later on a not-yet-started season the same way `categories` are mutated. `get_ideas` reads the current season's `questionTypes` (when one exists), falling back to `config.trivia.questionsTypes` otherwise (or when `now` falls in a gap between seasons). No caching — read on every `get_ideas` call.
- Update `triviaCheckInstruction` so admins discover that they can configure question types per season or workspace-wide.

## Capabilities

### New Capabilities

- `trivia-choice-questions`: the choice-question lifecycle — config schema (`questionsTypes` weighted-random, `choices.min`/`max`), `TriviaQuestion` type discriminator, `choices` + `correctIndex` storage, `get_ideas` weighted type pick + choice-count/index rolls, `save_question` choice-path validation, the "write correct first + distractor plausibility gate" generation flow, choice Block Kit card layouts (stacked + inline), reaction-array sizing, reveal-flow re-ordering (resolve-then-parse), choice-branch reaction parsing, multi-react silent void, and the choice-question admin-error path for unresolvable reveals.

### Modified Capabilities

- `trivia-batch-answers`: `submit_answers` accepts an optional `answerIndex: number` per answer entry, used for choice questions. Correctness for choice answers compares `answerIndex` to the stored `correctIndex`; boolean answers continue to compare `answer` to `isTrue`. The per-user result shape is unchanged.
- `trivia-question-search`: `find_previous_questions` returns the `type`, `choices`, and `correctIndex` fields on choice questions (in addition to the existing boolean fields). Duplicate-detection keyword search is unchanged — same-fact cross-type duplicates are not deduped (different question shapes).
- `trivia-scheduled-prompts`: the question-posting flow branches on `suggestedType` from `get_ideas` (boolean path unchanged; choice path adds correct-first/distractor-gate/choice-card-layout steps); the reveal flow resolves the question before parsing reactions and branches on `question.type`; multi-react voters on choice questions are silently voided rather than roasted as fence-sitters.
- `trivia-seasons`: the `seasons.json#seasons[]` `SeasonEntry` schema gains an optional `questionTypes: Record<"boolean" | "choice", number>` field (mirrors the existing `categories: string[]` field — set per-entry, scoped to that season). The `upsert_season` MCP tool gains an optional `questionTypes` argument that is stored on the entry verbatim on create, and is replaceable on update for not-yet-started entries (mutating it on an already-started season is rejected, same constraint as `startedAt`). When the field is absent on an entry, the workspace-level `config.trivia.questionsTypes` is used. When seasons are disabled or `now` falls in a timeline gap, the workspace-level config is the sole source.

**Coordination with `refactor-seasons-as-timeline`:** this change targets the post-timeline `trivia-seasons` model (`seasons.json#seasons[]`, `upsert_season`, `findCurrentSeason`) which is implemented in `src/plugins/trivia/` already but whose spec deltas live in the unarchived `refactor-seasons-as-timeline` change. This change MUST archive after `refactor-seasons-as-timeline`. If sequencing changes, the `trivia-seasons` delta in this change SHALL be rebased onto whatever `trivia-seasons` baseline exists at archive time (mechanically: `upsert_season` ↔ `start_new_season`, `seasons.json#seasons[]` ↔ `seasons.json#current`).

## Impact

- **Code**: `src/plugins/trivia/` — `types.ts` (discriminator + optional choice fields on `TriviaQuestion`, optional `answerIndex` on `SubmittedAnswer`), `saveQuestion.ts` (choice-path validation), `submitAnswers.ts` (choice-path correctness), `getIdeas.ts` (weighted type roll + choice-count/index rolls + season-vs-config read), `scheduledPrompts.ts` (rewritten `SEND_QUESTIONS_INSTRUCTIONS` and `PROCESS_RESPONSES_INSTRUCTIONS` with type-branches), `findPreviousQuestions.ts` (return extra fields), `data.ts` (season-types accessors if seasons enabled), `triviaCheckInstruction.ts` (admin discovery copy).
- **Config**: `data/config.json` gains optional `trivia.questionsTypes` (weighted-random map) and `trivia.choices.{min,max}` (defaults 2 and 4). Default behavior with both omitted (or `questionsTypes` = `{ "boolean": 1 }`) is unchanged from today.
- **Data files**: `questions.json` entries gain optional `type`, `choices`, `correctIndex` fields when written from this change forward. `answers.json` entries gain optional `answerIndex`. `seasons.json` (introduced by `add-trivia-seasons`) gains optional `questionTypes` and `choices` fields on each season record. Legacy entries without these fields read as boolean — no backfill migration needed.
- **Dependencies**: depends on `add-trivia-seasons` landing first (the season-override path references `seasons.json` and `start_new_season`'s schema). No new packages.
- **Tests**: `getIdeas` weighted-random distribution (statistical check over many calls), `getIdeas` season-vs-config priority, `saveQuestion` choice validation (length bounds, single-correct-index, duplicate choice strings), `submitAnswers` choice correctness, distractor plausibility gate scenarios (gate-failure rewrite path), reveal-flow choice-branch parsing (correct/incorrect/multi-react/wildcard categorization), reveal hard-failure when choice question cannot be resolved.
- **Backward compatibility**: fully backward-compatible. Legacy `TriviaQuestion` rows without `type` read as boolean. Legacy `SubmittedAnswer` rows without `answerIndex` read as boolean answers. Deployments with `trivia.questionsTypes` omitted or set to `{ "boolean": 1 }` behave exactly as today.
