## Why

Today, a trivia game's question cron fire does both heavy work and presentation in a single Claude run: generate the question(s), then post to Slack. Generation latency (which can be considerable for multi-slot formats with topical research) directly delays the post. Failures during generation either drop the post entirely or leave Claude in a partially-posted state. There is also no way for admins to pre-stage questions in advance — a pre-prepared pool ahead of the visible fire time would let generation absorb its own retries, network blips, and self-review reframes without keeping users waiting at fire time.

Splitting question generation from question posting along a new "PREP" schedule introduces a staging buffer: PREP runs ahead of the post cron, calls only the gen-and-save tools, and writes to disk without posting. POST keeps the existing question-cron timing, reads the oldest staged question per slot, and ships them — with an inline-generation fallback when the buffer is empty so the channel never goes silent on a missed prep run.

This also lays the groundwork for a future "one Claude per question" model where each slot is generated by its own parallel run — the per-slot staged-pool design generalizes cleanly because there is no batch container to coordinate.

## What Changes

- Add `TriviaGame.prepCron?: string` — an **optional** cron expression authored separately by the admin. When present, the plugin emits a third channelless cron spec per game (`<name>:prep`) on top of the existing `:question` and `:reveal` specs. When absent, the existing two-cron behavior is unchanged.
- Mark the prep spec channelless (omit `CronJobSpec.channel`) so the SDK structurally restricts `submit_response` to `{ skip_response: true }` for that run. Prep can never deliver a Slack message by construction.
- Restrict the prep cron's `requiredTools` to `[get_ideas, find_previous_questions, save_question]` (no `post_questions`). Two layers of "prep cannot post": the channelless `submit_response` lock AND the missing tool from the allowlist.
- Add a new `PREP_QUESTIONS_INSTRUCTIONS` prompt — the gen-only fill loop. It calls `find_previous_questions({ posted: false, seasons: ["current"] })` first, learns the format via `get_ideas`, and only generates for slots that don't yet have a staged question. Self-terminates with `submit_response({ skip_response: true })` after the last save.
- Add a new `POST_QUESTIONS_INSTRUCTIONS` prompt — used by the question cron of games WITH `prepCron` configured. Structure: (1) read staged pool via `find_previous_questions({ posted: false, seasons: ["current"] })`, (2) for each format slot index, identify the oldest staged question, (3) for any missing slot, fall back to the per-slot generation flow inline, (4) build the date-stamped opener + per-question flair blocks from question data + persona, (5) call `post_questions`.
- **Keep `SEND_QUESTIONS_INSTRUCTIONS` UNCHANGED in observable behavior** for games WITHOUT `prepCron` — they continue to use the legacy gen-and-post prompt with no staged-pool check overhead. Internally, `SEND_QUESTIONS_INSTRUCTIONS` is reconstructed from shared building blocks (`PER_SLOT_GENERATION_PATHS`, `FORMAT_AND_POST_SECTION`, `CONTEXT_PRIORITY_PREAMBLE`) so that downstream evolutions of the per-slot generation logic propagate to all three prompts automatically. Games opting out of prep pay zero new overhead.
- Extend `find_previous_questions` with a new optional `posted?: boolean` filter — `true` = only `postedAt !== undefined` (today's behavior when omitted is "all questions; criterion ignored"), `false` = only `postedAt === undefined` (the staged pool). The filter participates in the existing `match: "all" | "any"` combinator like any other criterion.
- Update `upsert_game` to accept `prepCron` and update the admin instruction guidance so Claude proposes a sensible prep cron (e.g., 30 minutes before `questionCron`) when an admin sets up a game without supplying one. Cron arithmetic — including day/week boundary handling — lives in Claude's reasoning at game-setup time, **not** in bot code.
- Propagate the game's `skipDates` (off-days) to all emitted specs uniformly — prep, question, and reveal all skip on the same dates.
- Pool selection at post time scopes to the current season (`season === currentSlug`). Staged records belonging to closed seasons stay on disk but are ignored by post-time picking — a season rollover between prep and post drops the orphans cleanly.
- Format snapshot semantics arrive for free via the existing `slot.index` and `slot.label` stamped by `save_question`. No new snapshot field is added. The "format snapshot" is the set of staged questions in the pool: questions inherit their slot identity at save time and are unaffected by mid-window format edits.

## Capabilities

### New Capabilities

- `trivia-question-prep`: defines the prep cron spec shape, the channelless restriction, the prep-cron tool allowlist (`get_ideas`, `find_previous_questions`, `save_question` only), the PREP prompt's fill-loop contract (staged-pool query, per-slot fill semantics, no-op when complete), and the prep/post handoff contract (staged records flow through the existing `TriviaQuestion` shape with `postedAt === undefined`).

### Modified Capabilities

- `trivia-games`: add the optional `prepCron` field to `TriviaGame`; surface via `list_games` when set; document the cascade behavior alongside the existing per-game fields.
- `trivia-question-posting`: rename and restructure the question-cron prompt to start with a staged-pool query and fall back to inline generation for missing slots; unify the per-fire flow regardless of whether prep is enabled.
- `trivia-question-search`: add the `posted?: boolean` filter to `find_previous_questions` and document its interaction with the `match` combinator.
- `trivia-managed-schedules`: extend `buildGameSpecs` to emit the third (prep) cron spec when `prepCron` is set; propagate `skipDates` uniformly across all emitted specs.

## Impact

- **Code**:
  - `src/plugins/trivia/core/configTypes.ts` — add `prepCron?: string` on `TriviaGame`.
  - `src/plugins/trivia/core/configParsers/games.ts` (or equivalent) — validate `prepCron` as a non-empty cron string via `CronExpressionParser.parse` when present; drop with a logged warning on invalid.
  - `src/plugins/trivia/domain/buildGameSpecs.ts` — emit a third spec `<name>:prep` (channelless) when `game.prepCron` is set; propagate `skipDates` to all three specs; add a `PREP_REQUIRED_TOOLS` constant excluding `post_questions`; pass the new `PREP_QUESTIONS_INSTRUCTIONS` prompt with `{game}` substituted.
  - `src/plugins/trivia/prompts/scheduledPrompts.ts` — extract `STAGED_POOL_CHECK_AND_DISPATCH`, `PER_SLOT_GENERATION_PATHS`, `FORMAT_AND_POST_SECTION` building blocks. Reconstruct `SEND_QUESTIONS_INSTRUCTIONS` from those blocks (zero observable behavior change). Add new `PREP_QUESTIONS_INSTRUCTIONS` (gen-only, channelless, terminates with `submit_response(skip)`) and `POST_QUESTIONS_INSTRUCTIONS` (staged-pool check + inline-gen fallback + full FORMAT_AND_POST_SECTION).
  - `src/plugins/trivia/tools/questions/findPreviousQuestions.ts` — extend the schema with `posted?: boolean`; thread the filter through the existing combinator logic.
  - `src/plugins/trivia/tools/games/listGames.ts` — surface `prepCron` per-game when set.
  - `src/plugins/trivia/tools/games/upsertGame.ts` (and the management instruction) — accept and validate `prepCron`; admin-instruction guidance for Claude to propose a sensible default at setup time.
- **Tests**:
  - parser unit tests for `prepCron` (valid cron, invalid cron, omitted);
  - `buildGameSpecs` tests for the 2-spec vs 3-spec emission, channelless prep spec, required-tools restriction, `skipDates` propagation;
  - `findPreviousQuestions` tests for `posted: true` / `posted: false` / omitted with all combinator modes;
  - prompt builder tests confirming PREP excludes the FORMAT & POST section and POST includes the staged-pool prefix;
  - `listGames` tests for `prepCron` surfacing;
  - integration tests covering: prep populates pool → post picks oldest per slot → reveal proceeds; partial pool → post falls back to inline gen for missing slots; admin-pre-generated batch → next prep is a no-op.

- **Migrations**: none required. Existing games without `prepCron` retain today's two-cron behavior unchanged.
- **i18n strings**: none required — prep is internal, post-prompt flair already routes through the existing i18n surfaces (date opener, season opener, etc.).
